# draft-mode — ทำงานบนฉบับร่าง ไม่กระทบเว็บจริง 📝

ช่วยนักเรียนทดลองอะไรใหม่ๆ ใน "ฉบับร่าง" (git branch) ที่แยกจากเว็บจริง ลองพังได้ ลบทิ้งได้ ถ้าถูกใจค่อยใช้

---

## กฎหลัก

- **ภาษาไทยเรียบง่ายเสมอ** — assume นักเรียนไม่รู้จัก git branch
- **ห้ามใช้คำว่า "branch", "merge", "checkout", "stash", "rebase"** — ใช้คำเทียบเคียงเสมอ:
  - branch = **"ฉบับร่าง"** (draft branch) หรือ **"ฉบับจริง"** (main)
  - merge = **"เอาฉบับร่างไปใช้แทนฉบับจริง"**
  - checkout = **"สลับไปอีกฉบับ"**
  - commit = **"เซฟ"**
  - conflict = **"จุดที่ทับกัน"**
- **Windows** → `PowerShell`, ห้าม `&&`, ใช้ `Set-Location` แทน `cd`
- **macOS** → `Bash`, ใช้ `&&` ปกติ
- **ตรวจ state ก่อนเสมอ** — รู้ว่านักเรียนอยู่ตรงไหนของ flow

---

## Concept: 3 สถานะที่ skill ต้องรู้จัก

```
[main + ไม่มีฉบับร่างค้าง]  → flow START
[อยู่ใน draft branch]        → flow CONTINUE/FINISH
[main + มีฉบับร่างค้าง]      → flow RESUME/DISCARD
```

---

## ขั้นตอนที่ 1 — ตรวจ state

รัน:
- `git branch --show-current` → ได้ชื่อ branch ปัจจุบัน
- `git branch --list "draft/*"` → ได้รายชื่อ draft branches ที่มี
- `git status --short` → ดูว่ามี uncommitted changes ไหม

| state | เงื่อนไข | ไป flow ไหน |
|-------|---------|-------------|
| **A — สะอาด พร้อมเริ่ม** | branch = main + ไม่มี `draft/*` | **flow START** (ขั้น 2) |
| **B — กำลังทดลองอยู่** | branch ขึ้นต้น `draft/` | **flow MIDDLE** (ขั้น 3) |
| **C — มีฉบับร่างค้าง** | branch = main + มี `draft/*` | **flow RESUME** (ขั้น 4) |

ถ้าไม่ได้อยู่ใน git repo (`git remote -v` ว่าง) → แจ้ง: "ยังไม่ได้เชื่อมโฟลเดอร์กับ GitHub พิมพ์ `/connect-repo` ก่อนนะคะ/ครับ"

## flow START — เริ่มฉบับร่างใหม่ (ขั้น 2)

### 2.1 ถ้ามีงานค้าง (uncommitted) ก่อนสร้างฉบับร่าง

ถาม:
> "เห็นว่ามีงานที่ยังไม่ได้เซฟอยู่บ้าง — เซฟลงฉบับจริง (main) ก่อนสร้างฉบับร่างไหมคะ/ครับ?
> (A) เซฟลงฉบับจริงก่อน ค่อยสร้างฉบับร่าง
> (B) เอาทั้งงานที่ค้างนี้ไปอยู่ในฉบับร่างเลย"

- (A) → `git add .` → `git commit -m "เซฟงานก่อนทดลอง"` → ขั้น 2.2
- (B) → ขั้น 2.2 ทันที (changes จะ carry over)

### 2.2 ถามนักเรียนว่ากำลังจะลองอะไร

> "กำลังจะลองอะไรคะ/ครับ? บอกสั้นๆ พอ (เช่น 'ลองหน้าเว็บแบบใหม่', 'ลองเปลี่ยนสี')"

ใช้คำตอบสร้างชื่อฉบับร่าง — แปลงเป็น kebab-case อังกฤษ (ถ้าตอบเป็นไทย → transliterate หรือ summarize เป็นอังกฤษสั้นๆ)

ตัวอย่าง:
- "ลองหน้าเว็บแบบใหม่" → `new-layout`
- "ลองเปลี่ยนสี" → `color-change`
- "ลอง hero ใหม่" → `new-hero`

### 2.3 สร้างฉบับร่าง

ชื่อ branch = `draft/YYYY-MM-DD-<slug>` เช่น `draft/2026-05-26-new-hero`

รัน `git checkout -b draft/<วันที่>-<slug>`

### 2.4 แจ้งนักเรียน

> "📝 สร้างฉบับร่างเรียบร้อยแล้วค่ะ/ครับ!
>
> ✏️ **ตอนนี้คุณอยู่ใน:** ฉบับร่าง [ชื่อ]
> 🏠 **ฉบับจริง (เว็บ live):** ยังเหมือนเดิม ไม่กระทบ
> 💡 **ลองอะไรก็ได้เต็มที่** — ลบ แก้ พังได้ ไม่เป็นไร
>
> 🔚 **เมื่อเสร็จ:** พิมพ์ `/draft-mode` หรือ 'จบฉบับร่าง' — ผมจะถามว่าจะใช้, ทิ้ง, หรือเก็บไว้ก่อนคะ/ครับ"

→ **จบ skill ที่นี่** ปล่อยให้นักเรียนทำงาน

## flow MIDDLE — กำลังทำฉบับร่างอยู่ (ขั้น 3)

นักเรียนพิมพ์ "draft-mode" ขณะอยู่ใน draft branch → แสดงว่าเขาอยากจบ (หรือดู status)

ถาม:
> "ตอนนี้คุณอยู่ในฉบับร่าง **[ชื่อ]** ที่เริ่มไว้เมื่อ [วันที่/เวลา]
>
> อยากทำอะไรคะ/ครับ?
> (A) ✅ **ใช้เลย** — เอาฉบับร่างนี้ไปแทนฉบับจริง (เว็บจริงจะเปลี่ยน)
> (B) 🗑️ **ทิ้ง** — ไม่ถูกใจ ลบฉบับร่างทิ้ง (ฉบับจริงไม่เปลี่ยน)
> (C) 📌 **เก็บไว้ก่อน** — กลับไปฉบับจริง แต่เก็บฉบับร่างไว้ทำต่อทีหลัง
> (D) 🔄 **ทำต่อ** — ยังไม่เสร็จ ปิดเมนูนี้ทำงานต่อ"

### 3.A — ✅ ใช้เลย (merge to main + push)

1. ตรวจ uncommitted → ถ้ามี → `git add .` → `git commit -m "เซฟก่อนใช้ฉบับร่าง"`
2. จำชื่อ draft branch ปัจจุบันไว้ใช้ขั้นถัดไป
3. `git checkout main`
4. `git merge <draft-branch> --no-ff -m "เอาฉบับร่าง <slug> มาใช้"`
5. **ถ้า merge สำเร็จ (no conflict):**
   - `git branch -d <draft-branch>` (ลบ branch หลัง merge เสร็จ)
   - **กรณีพิเศษ ตัวอย่างจาก Claude Code (ชื่อ branch ลงท้าย `-claude-code-design`):**
     ไฟล์ที่เพิ่ง merge มาเป็น Path B ที่ยังไม่เคยผ่าน web-import จึงยังไม่ได้เก็บงานภาษาไทย
     และยังไม่ได้ใส่ค่าจริงแทน placeholder **ห้าม push ทันที** ให้ **invoke `Skill(web-finish)` ก่อน**
     web-finish จะเก็บงาน + ใส่ค่าจริง + เปิด preview ให้ student เห็นก่อน แล้วค่อย push ผ่าน `/save-work`
     ตอน student พอใจ จากนั้นข้ามไป "แจ้ง" ด้านล่าง
   - **กรณีปกติ (ฉบับร่างทั่วไป):** `git push origin main`
   - แจ้ง: "✅ เอาฉบับร่างไปใช้บนเว็บจริงเรียบร้อยแล้วค่ะ/ครับ! 🎉 เว็บจริงอัพเดทแล้ว
     >
     > 💡 *ถ้าเปลี่ยนใจ พิมพ์ 'ย้อนกลับ' หรือ `/undo` — เว็บจะกลับไปเหมือนเดิมได้*"
6. **ถ้า merge มี conflict** → ไปขั้น 5 (conflict handler)

### 3.B — 🗑️ ทิ้ง (delete draft)

ยืนยันก่อน เพราะลบแล้วกู้คืนไม่ได้ง่าย:
> "⚠️ จะลบฉบับร่าง **[ชื่อ]** ทิ้งจริงๆ ใช่ไหมคะ/ครับ? (งานในฉบับร่างจะหายหมด รวมถึงไฟล์ที่ยังไม่ได้เซฟด้วย ฉบับจริงไม่กระทบ)"

ถ้ายืนยัน:
1. **ก่อนสลับ branch** — commit ทั้งงานค้างและไฟล์ใหม่ที่ยังไม่ได้ track เพื่อให้ทุกอย่างผูกกับ draft branch (ถ้าไม่ commit ไฟล์ untracked จะค้างในโฟลเดอร์หลังลบ branch):
   - `git add -A` (รวม untracked files ด้วย `-A` ไม่ใช่ `.`)
   - `git commit -m "เซฟก่อนลบฉบับร่าง" --allow-empty` (`--allow-empty` กันกรณีไม่มีอะไรเปลี่ยน)
2. `git checkout main` — ตอนสลับ git จะลบไฟล์ที่ไม่อยู่ใน main ออกจากโฟลเดอร์อัตโนมัติ
3. `git branch -D <draft-branch>` (force delete เพราะไม่ได้ merge — ลบทั้ง history ของ draft)
4. **safety sweep** — `git clean -fd` เพื่อกวาดไฟล์ untracked ที่อาจยังหลงเหลือ (ไม่ลบ ignored files)
5. ตรวจสะอาดจริง: `git status` ควรเห็น `nothing to commit, working tree clean`
6. แจ้ง: "🗑️ ลบฉบับร่างเรียบร้อยแล้วค่ะ/ครับ ตอนนี้คุณอยู่ในฉบับจริง เว็บจริงไม่ได้กระทบเลย สะอาด 100% ✨"

### 3.C — 📌 เก็บไว้ก่อน (keep branch, return to main)

1. ตรวจ uncommitted → ถ้ามี → `git add .` → `git commit -m "เซฟค้างไว้ ทำต่อทีหลัง"`
2. `git checkout main`
3. แจ้ง: "📌 เก็บฉบับร่าง **[ชื่อ]** ไว้แล้วค่ะ/ครับ ตอนนี้กลับมาฉบับจริง — กลับมาทำต่อเมื่อไหร่ก็ได้ พิมพ์ `/draft-mode` ก็จะเจอฉบับร่างที่ค้างไว้"

### 3.D — 🔄 ทำต่อ

> "👍 ทำต่อได้เลยค่ะ/ครับ พิมพ์ `/draft-mode` อีกครั้งเมื่อเสร็จนะคะ/ครับ"

จบ skill

## flow RESUME — มีฉบับร่างค้าง (ขั้น 4)

นักเรียนอยู่บน main แต่มี `draft/*` branch ค้าง → เขามักจะลืม

แสดง:
> "เจอฉบับร่างที่เก็บไว้ค้าง:
> - **[ชื่อ draft branch 1]** (เริ่มเมื่อ [วันที่])
> - **[ชื่อ draft branch 2]** (ถ้ามี)
>
> อยากทำอะไรคะ/ครับ?
> (A) 🔄 **เข้าไปทำต่อในฉบับร่างนี้**
> (B) ✅ **ใช้เลย** — เอาฉบับร่างนี้ไปแทนฉบับจริง
> (C) 🗑️ **ทิ้ง** — ลบฉบับร่างทิ้ง
> (D) ➕ **สร้างฉบับร่างใหม่** (ของเก่ายังอยู่)"

- (A) → `git checkout <branch>` → แจ้งว่ากลับมาแล้ว
- (B) → ทำตาม flow 3.A
- (C) → ทำตาม flow 3.B
- (D) → ไป flow START (ขั้น 2)

ถ้ามี draft หลายอัน → ให้นักเรียนเลือกก่อนว่าจะทำกับอันไหน

## ขั้นตอนที่ 5 — Handle Conflict (จุดที่ทับกัน)

ถ้า `git merge` ออกมามี conflict — **ห้าม panic** **ห้ามใช้คำว่า "conflict"** เรียกว่า **"จุดที่ทับกัน"**

### 5.1 รวบรวมไฟล์ที่มีจุดทับกัน

รัน `git diff --name-only --diff-filter=U` → list ไฟล์ที่ conflict

### 5.2 ลอง auto-resolve ก่อน

ถามนักเรียน:
> "เจอ **[N] จุดที่ทับกัน** ในไฟล์: [list]
>
> 💡 ส่วนมากเลือกได้ง่ายๆ คุณอยากให้ผมจัดการยังไงคะ/ครับ?
>
> (A) **ใช้แบบใหม่ทั้งหมด** (ของในฉบับร่างที่เพิ่งทำ) — เหมาะถ้าทำใหม่ทับของเก่า
> (B) **ใช้แบบเก่าทั้งหมด** (ของในฉบับจริง) — เหมาะถ้าเปลี่ยนใจ ไม่อยากเอาของใหม่
> (C) **ดูทีละจุดแล้วเลือก** — ผมจะแสดงให้ดูทีละไฟล์
> (D) **ให้ผมลองรวมให้** — ผมจะลองผสมทั้งสองแบบ ถ้าออกมาแปลกจะเตือน"

### 5.3 ทำตามที่เลือก

**(A) ใช้แบบใหม่ทั้งหมด:**
- `git checkout --theirs <conflict-files>` (เทียบฉบับ — theirs คือฉบับร่างเพราะกำลัง merge เข้า main)
- `git add <conflict-files>`
- `git commit --no-edit`
- push → จบ ✅

**(B) ใช้แบบเก่าทั้งหมด:**
- `git checkout --ours <conflict-files>`
- `git add <conflict-files>`
- `git commit --no-edit`
- push → จบ ✅

**(C) ดูทีละจุด:**
สำหรับแต่ละไฟล์:
1. อ่านไฟล์ → หา `<<<<<<<` `=======` `>>>>>>>` markers
2. แสดงให้นักเรียนเห็นแบบเทียบ:
   > "ไฟล์: `index.html` บรรทัด 23
   >
   > **แบบเก่า (ฉบับจริง):**
   > ```
   > <h1>เครื่องเสียงรถยนต์</h1>
   > ```
   >
   > **แบบใหม่ (ฉบับร่าง):**
   > ```
   > <h1>ติดเครื่องเสียงรถยนต์ครบวงจร</h1>
   > ```
   >
   > เลือก: (A) เก่า / (B) ใหม่ / (C) เขียนเองใหม่ / (D) เอาทั้งสองแบบมารวมกัน"
3. เขียนทับไฟล์ตามที่เลือก (ลบ markers ออก)
4. `git add <file>`
5. ทำต่อจนครบ → `git commit --no-edit` → push → จบ ✅

**(D) ลองรวมให้:**
- พยายาม merge เนื้อหาทั้งสองแบบเข้าด้วยกัน (Claude ใช้ context เดา)
- หลัง merge → แสดงผลให้นักเรียนดู → ถามว่า ok ไหม
- ถ้า ok → commit + push
- ถ้าไม่ ok → fall back ไป (C) ทีละจุด

### 5.4 ถ้า auto-resolve แล้วยัง error

แทนที่จะบอก "ขอผู้ช่วยมนุษย์" → ให้ทางเลือกใหม่:
> "การรวมยังมีปัญหานิดหน่อย ลองทางอื่นกันคะ/ครับ:
> (A) ย้อนการรวมทั้งหมด กลับไปฉบับร่าง (`git merge --abort`) แล้วลองทีละจุด
> (B) ลบฉบับร่างทิ้ง เริ่มใหม่
> (C) แสดง error ให้ดู (สำหรับคนเทคนิค)"

## State Awareness — pattern สำหรับ skill อื่น

skill อื่นทุกตัวที่จะแก้ไฟล์ ควรเริ่มต้นด้วยการตรวจว่านักเรียนอยู่ฉบับไหน เพื่อแจ้งให้นักเรียนรู้ตัว (กันลืม)

**Pattern (1 บรรทัดก่อนเริ่มงาน):**

รัน `git branch --show-current` → ถ้าขึ้นต้น `draft/` → แสดงบรรทัดเดียวเตือน:

> "📝 *(หมายเหตุ: คุณอยู่ในฉบับร่าง [ชื่อ] — การเปลี่ยนแปลงจะไม่กระทบเว็บจริงจนกว่าจะตัดสินใจใช้ผ่าน `/draft-mode`)*"

ถ้าอยู่บน `main` ไม่ต้องแสดงอะไร (ทำงานปกติ)

**ไม่ต้องถาม ไม่ต้องหยุด** — แค่แจ้งให้รู้ตัว แล้วทำงานต่อตาม flow ของ skill นั้นๆ

## สิ่งที่ต้องระวัง

- **อย่าใช้คำเทคนิค** กับนักเรียนเด็ดขาด (`branch`, `merge`, `conflict`, `stash`, `rebase`)
- **อย่า force push** ไม่ว่ากรณีใด — beginner เสี่ยงเสียงานหมด
- **อย่า merge เข้า main โดยไม่ถาม** — ต้องผ่าน flow 3.A เสมอ
- **อย่าลบ draft branch โดยไม่ยืนยัน 2 ครั้ง** เผื่อนักเรียนเปลี่ยนใจ
- ถ้า push ขึ้น GitHub ไป → ลบ remote branch ด้วย `git push origin --delete <branch>` (เฉพาะ draft ที่ push แล้วและจะทิ้ง)
- ถ้าเจอ error ที่ skill นี้ไม่ครอบคลุม → อธิบายเป็นไทยง่ายๆ + ให้นักเรียน 2-3 ทางเลือก (อย่าโยน raw error)
- ปกติ draft branch ไม่ต้อง push ขึ้น GitHub (ไม่ทำให้รก) — push แค่ตอน merge เข้า main เท่านั้น
